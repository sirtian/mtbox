## 1. 系统边界与运行模型

### 1.1 进程与线程

- **单进程**：FastAPI（Uvicorn）+ APScheduler（BackgroundScheduler，线程池）。
- Web 路由一律写成同步 `def`，由 Starlette 放进线程池执行；避免同步 httpx / sqlite 阻塞事件循环。
- 定时任务同样跑在线程池；每个任务 `max_instances=1`、`coalesce=True`，天然防重入。
- 搜索是全局串行资源：进程内 `threading.Lock` + 限速器，保证同一时刻只有一个搜索在跑。
- 不引入 Redis、消息队列、独立 worker。
- **必须以单 worker 运行**（`uvicorn ... --workers 1`）：限速器、调度锁、登录节流都是进程内状态。
- 容器以非 root 运行时，必须保证 `LIBRARY_DIR` 可写、且对 `DOWNLOAD_DIR` 有读权限（硬链接还要求同一文件系统）。

### 1.2 数据流

```
Web/API ──► Service ──► SQLite
                │
                ├──► MTeamClient ──► api.m-team.cc
                ├──► QBClient ────► qBittorrent
                └──► Organizer ───► 硬链接 ──► 极影视目录

APScheduler ──► 同一组 Service（与 Web 共用，无第二套逻辑）
```

**原则：所有业务逻辑只存在于 `services/`，Web 与调度器都只是调用方。**

### 1.3 时间与路径约定

- 数据库时间统一存 **UTC ISO-8601**（`2026-10-26T03:21:00Z`），展示时按 `TZ` 转本地。
- 路径分两套命名空间：
  - **qB 命名空间**：qB 容器内看到的路径，如 `/downloads`。
  - **本容器命名空间**：本容器看到的路径，如 `/downloads` 或 `/data/downloads`。
  - 两者通过 `PATH_MAP_JSON` 映射，默认相同。
- 所有用户可见路径在入库前做规范化（`posixpath.normpath`），拒绝 `..` 越界。

### 4.2 迁移策略

- `schema_meta.version` 记录版本号；`migrations.py` 里是 `list[tuple[int, list[str]]]`。
- 启动时在事务内逐版本执行，失败回滚并拒绝启动。
- 不做向下迁移；升级前用 `cli backup`。

### 4.3 清理策略（每日）

- `api_call`：保留 25 小时。
- `event_log`：保留 30 天。
- `torrent`：
  - `state='candidate'` 且超过 `candidate_ttl_days` → 删除；
  - `state='ignored' AND ignored_by='auto'` 且超期 → 删除（下次可重新评估）；
  - `state='ignored' AND ignored_by='manual'` → **永久保留**，否则同一种子会反复出现。
- `account_snapshot`：保留 30 天。

### 4.4 事务与并发

- 每个请求/任务开独立连接：`sqlite3.connect(path, timeout=5)`，`row_factory=sqlite3.Row`。
- 写操作统一走 `db.tx()` 上下文，`BEGIN IMMEDIATE`。
- 抢占用乐观锁：`UPDATE torrent SET state='grabbed' WHERE id=? AND state='candidate'`，`rowcount==1` 才算抢到。
- SQLite 单写者，写冲突靠 `busy_timeout=5000` 重试；不跨进程。`BEGIN`/`COMMIT` 遇到 `locked`/`busy` 时再按 0.2s、0.4s 退避重试（最多 3 次），覆盖 NAS 磁盘慢或升级期间新旧容器共用数据库的情况。
- 回滚前检查 `conn.in_transaction`：SQLite 在部分错误（磁盘满、IO 错误）后会自行回滚，此时再执行 `ROLLBACK` 会抛 “cannot rollback - no transaction is active” 并掩盖原始异常；检测到事务已结束则直接抛出原始异常。

## 5. 状态机

### 5.1 订阅

```
active ──暂停──► paused ──恢复──► active
  │
  ├── 电影已整理 / 剧集到达 episode_to 且全部整理 ──► done
  └── done 可由用户手动恢复为 active
```

`error_count` 不改变 `status`，只拉长下次检查时间：
`next_check = last_checked_at + interval_min × 2^min(error_count, 4)`，上限 24h。

### 5.2 种子任务

```
                 ┌──────────── ignore（人工/低分/预算/重复）──────────┐
                 │                                                    ▼
candidate ──grab──► grabbed ──qB 确认──► downloading ──进度=1──► completed ──整理──► organized ──清理──► deleted
   ▲                  │                     │                        │
   │                  └── 取种/添加失败 ──► failed                   └── 整理失败 ──► organize_failed
   └──────────────── 重试（failed → candidate） ◄──────────────────────────────────────┘
```

允许的迁移（其余一律拒绝）：

| from | to |
|---|---|
| `candidate` | `grabbed`, `ignored` |
| `grabbed` | `downloading`, `failed` |
| `downloading` | `completed`, `failed` |
| `completed` | `organized`, `organize_failed` |
| `organize_failed` | `organized` |
| `failed` | `candidate`（人工重试） |
| `organized` | `deleted` |
| `ignored`（`ignored_by='auto'`） | `candidate`（后续搜索重新达标时复活） |
| `ignored`（`ignored_by='manual'`） | —（终态） |

例外：用户从任务页「删除」是**任意状态 → `deleted`**（同时删除 qB 种子与文件），
任务随即从所有任务视图消失；未整理的 `episode_state` 一并删除，后续检查可重新抓取，
已整理分集保持不变。该软删除保留记录用于审计，不会变成 `failed` 留在列表中。

### 5.3 分集状态

- 仅在 `grabbed` 及之后写入。
- 一个合集种子覆盖多集时，写多行，指向同一 `torrent_id`。
- `organized` 是终态；即使种子后来被删除，分集状态仍保留，用于"不重复下载"。
- 状态只能**单调前进**：`grabbed → downloading → completed → organized`，任何批量/轮询更新都不得把 `organized` 改回更早状态。

### 5.4 幂等约束

- 同一 `mt_id` 只允许一条 `torrent` 记录。
- 同一 `(subscription_id, season, episode)` 只允许一条 `episode_state`。
- 自动忽略必须带 `ignored_by='auto'`，允许后续搜索复活；人工忽略 `ignored_by='manual'` 永久生效。
- `grab` 以 `candidate → grabbed` 的条件更新作为互斥锁，重复点击返回当前状态，不重复调用 MT。
- qB 添加前先用本地计算的 `info_hash` 查一次；已存在则直接接管。

## 6. 客户端设计

### 6.1 错误模型

```python
class MTeamError(Exception): ...
class MTeamAuthError(MTeamError): ...        # 密钥无效/权限不足
class MTeamRateLimitError(MTeamError): ...   # 429/403/Cloudflare 1010
class MTeamApiError(MTeamError):             # code != 0
    code: str; message: str
class MTeamNetworkError(MTeamError): ...     # 超时/连接失败
class BudgetExceeded(MTeamError): ...
class CooldownActive(MTeamError): ...
class RateLimitBusy(MTeamError):              # 手动搜索拿不到限速槽位
    retry_after: int
```

分类规则：

- HTTP 401/403 或包内容提示密钥问题 → `MTeamAuthError`（**不重试**，暂停调度 + 通知）。
- HTTP 429 / 正文含 `1010` / Cloudflare 页面 → `MTeamRateLimitError`（退避，连续 3 次进冷却）。
- JSON 可解析且 `code != 0` → `MTeamApiError`（不重试）。
- 超时、连接错误、5xx → `MTeamNetworkError`（重试 3 次：2s/4s/8s）。

### 6.2 `MTeamClient`

```python
@dataclass(frozen=True)
class MTeamTorrent:
    id: str
    name: str
```

### 6.6 `DoubanClient`

只用公开接口，不带账号、Cookie 或 API Key。

| 用途 | 接口 | 关键参数 |
|---|---|---|
| 剧集/电影/综艺榜单（含筛选） | `GET /rexxar/api/v2/{tv\|movie}/recommend`（综艺用 `tv`） | `start`、`count`、`sort=U/R/S`、`tags`（综艺固定 `综艺`，筛选时追加类别与年份，逗号分隔，如 `悬疑,2024`、`综艺,真人秀,2024`） |
| 剧集/综艺总集数 | `GET /rexxar/api/v2/tv/{id}` | 读取 `episodes_count`、`last_episode_number`、`original_title`、`aka`、`year` |

实现要点：

- `fetch(kind, sort, start, count, year, genre, refresh)` 统一返回 `DoubanChart`；
  缓存键包含 `kind/sort/start/count/标签串`，默认缓存 600 秒，网络或解析
  失败时回退旧缓存并标记 `stale`。
- 三种榜单统一走 rexxar recommend：综艺固定带 `tags=综艺`（否则会混入普通
  剧集），设置年份或类别后再追加对应标签（如 `悬疑,2024`、`2020年代`、
  `综艺,真人秀,2024`）。不使用网页版 `new_search_subjects`：它的电视类别索引
  很稀疏，`电视剧` + `纪录片` 只能返回个位数条目，而 `tags=纪录片` 能返回
  完整的纪录片目录（`total` 约 500）。也不再用综艺专用的
  `j/search_subjects`，统一接口后才拿得到总条数、年份与评分人数。
- 年份与类别都做白名单校验：年份是 `year_options()` 生成的单个年份或
  `2020年代/2010年代/…/更早`，类别是 `genre_options(kind)`（综艺单独一套）；
  非法值视为未筛选，不会拼进豆瓣请求。
- 年份标签直接作为 tag 发送，无需换算区间；接口同时返回每条的 `year`，
  单年与年代筛选都能显示年份。
- 筛选结果会混入豆瓣榜单集合（`type=chart`）和少量跨类型条目：只保留
  `type` 与 `kind` 匹配的条目，电影榜单里的剧集、剧集榜单里的电影都会被丢弃。
- 推荐接口返回 `total`（上限约 500，页面展示为“共约 N 条”），`has_more` 用
  `start + count < total` 判断；不能按过滤后的条数判断，否则遇到榜单条目会
  提前结束分页。若某一页豆瓣返回空列表，即使 `total` 仍大于 `start` 也结束
  翻页，避免在豆瓣实际目录见底后一直出现空页。
- 推荐接口单次最多返回 50 条，即使请求 `count=100`。因此每页 100 条时拆成
  两次 50 条请求（`start` / `start+50`），按条目 ID 去重后合并。
- 每页条数由 `/douban?size=` 控制，只接受 20/50/100，默认 20；切换每页条数
  时回到第一页。跳页框提交 `page=N`，路由换算为 `start=(N-1)*size`；
  年份/类别/每页条数会作为隐藏字段一起提交，跳页不丢筛选。
- 分类/排序/翻页/跳页链接都保留当前筛选参数。
- 综艺条目按 `kind="tv"` 返回，订阅入口与普通剧集一致；预填季号从条目标题推断
  （`老友记 第二季` → 第 2 季），推断不到时用第 1 季。
- 豆瓣条目逐季建 subject（`老友记 第二季`），订阅检查时会用 subject 的
  `original_title`/`aka` 和标题里的季号补齐订阅的英文名、别名与季号（见 §8.2）。
- 所有文本截断到 500 字以内；海报只接受 `http(s)` URL，`javascript:` 等一律丢弃；
  年份、评分、集数均做范围校验。

### 7.4 评分

```python
def score(sub, item, parsed) -> float:
    q = sub.quality
    # 偏好列表内按顺序递减：2160p=1.0、1080p=0.7（差 9 分），列表外按基础档位
    s  = 30 * resolution_rank(parsed.resolution, q.resolutions)
    s += 20 if has_chinese_subs(item, parsed) else 0
    s += 4 if parsed.bit_depth == 10 and q.get("prefer_10bit", True) else 0
    s += 4 if (sub.kind == "movie" and q.get("prefer_chinese_audio", True)
               and has_chinese_audio(item.name, item.description, *item.labels)) else 0
    s += 15 if is_free(item.discount) else 0
    s += 15 * min(1.0, math.log10(item.seeders + 1) / 2)
    s += 10 * size_closeness(item.size_gb, q.prefer_size_gb) if q.prefer_size_gb else 6
    s += 5 * recency(item.created_at)        # 7 天内 1.0，30 天后 0
    s += 5 if parsed.group in q.group_whitelist else 0
    return round(s, 1)
```

默认偏好：`resolutions = ["2160p", "1080p"]`（4K 优先）、`prefer_10bit = true`、
`prefer_chinese_audio = true`（仅电影）。

- 10bit 与中文配音都是**软偏好**，单项 +4 分，两项合计 +8 分，小于 4K/1080p 的
  9 分差：因此“4K 8bit 无国语”仍优先于“1080p 10bit 国语”。
- 偏好可通过订阅 `quality` 覆盖：`resolutions` 调整顺序或删除 2160p，
  `prefer_10bit` / `prefer_chinese_audio` 置 `false` 关闭加分。
- `< min_score` → 落库为 `ignored`，原因"评分不足"，保留 7 天供查看。
- 分数相同：免费优先 → 做种多优先 → 发布新优先。


- `total_episodes` 在每次搜索后由 PT 描述更新：`全 46 集`、`47集全`、`共 12 期`
  等；持续更新的剧 PT 描述通常只有 `第 13-14 集`，此时用订阅的豆瓣 ID 请求
  豆瓣 subject 的 `episodes_count` 补全（每订阅成功查询一次后记录来源，避免重复）。
- `available_episode` 取本次搜索中同剧同季种子解析出的最大集数（含豆瓣
  `episodes_info`/`last_episode_number`），用于显示"待上线"；总集数未知时，
  它同时作为补齐/排序的目标上界（`1..available`），使发布较早的已播出单集
  不再被追新窗口挡掉。
- 已知总集数且未填 `episode_from` 时，目标范围自动视为 `1..total`，因此会补齐
  之前遗漏的集数；只想从某一集开始追，仍应填写起始集。

- 每个订阅返回最优**种子组合**：`Matcher.best_candidates()` 按 `subscription_id`
  分组，并把 `grab_plan` 的全部条目都返回，而不是只取 `ranked[0]`。例如已播
  20 集、候选只有 E01-E18 包和 E19-E20 包时，两行都标记为最优（1/2、2/2）；
  新集发布并进入候选后，重新计算计划会自动出现 3/3。每行带 `plan_index`、
  `plan_count`、`alt_count`（组合外备选数）；候选页默认 `view=best`。
  组合为空（都已下载或无候选可补）时回退显示单条最优，保持可见性。
  最优页调用 `grab_plan(ignore_limits=True)`，展示覆盖全部已播缺口的完整组合，
  **不受** `max_grabs_per_check` 和 `daily_download_budget_gb` 限制；实际自动
  下载仍按这两个上限分批执行，剩余集数由后续检查继续补齐。
- 只有 `Sxx`/`Complete` 而没有集数区间的合集无法确认实际内容：上传者可能把
  单集标成“S01 Complete”。此类行 `coverage_unknown=True`，保留潜在缺集数用于
  展示，但排序时排在所有可确认覆盖的种子之后，抓取计划只在可确认种子仍补不
  齐缺口时才把它作为兜底；绝不允许它单独满足整个缺口而隐藏其他种子。
- `view=all` 保留完整列表，供人工比较；前端不默认倾泻全部匹配结果。
- `auto_grab`、候选页展示、订阅行「下载最优」使用**同一套 `grab_plan`**，
  避免展示与自动抓取结果不一致。
- 候选页 `?sub=<订阅ID>` 过滤：`Matcher.candidates` / `best_candidates` 增加可选
  `subscription_id`，SQL 以 `t.subscription_id = ?` 限定；下拉框附带每个订阅的
  候选数，切换视图与单条操作都带回筛选参数。无效订阅 ID 在 GET 时回退“全部”，
  在批量删除 POST 时拒绝执行，避免误删。
- 批量删除（`candidates_delete` / `Matcher.delete_candidates`）：按当前订阅范围
  删除 `state='candidate'`，勾选 `include_ignored` 时连 `ignored` 一起删除；
  `grabbed/downloading/organized` 等已进入下载流程的记录永不匹配。删除前浏览器
  `confirm`，删除条数写入事件日志。
- 有明确集数范围时优先"一包补齐更多缺失集"的合集；追新订阅没有范围，按质量评分。
- 电影订阅存在 active 任务时不再产生第二条候选，避免重复下载不同发布。

抓取计划（`Matcher.grab_plan`，"下载最优"与自动下载共用）：

1. 目标范围用**已播出集数** `available_episode`（未知时退回 `total_episodes`，
   再退到显式 `episode_from/to`），减去 `episode_state` 已覆盖的集，得到待补集。
2. 按 §7.5 排序依次选取：候选覆盖的待补集非空才选中，选中后从待补集中扣除；
   直到待补集为空、达到 `max_grabs_per_check` 或日预算不足。
3. 一条**能确认覆盖范围**的合集若覆盖全部待补集，则只抓这一条。名字里只有
   `Sxx`/`Complete`、没有集数/`全N集`/`更新至N集` 的整季包覆盖范围未知，
   排在所有可确认种子之后；只有当可确认种子仍无法补齐缺口时才作为兜底抓取，
   由实际文件回填 `episode_state`，不会因为它的“Complete”标签而跳过其他种子。
4. 只有零散单集/区间包时，会一次抓取多条以补齐所有已播出集数。每条仍需通过
   §7.3 全部硬规则；非免费种子累计体积受 `daily_download_budget_gb` 限制。
   候选页展示时传 `ignore_limits=True`，只去掉条数/预算上限以显示完整组合。
5. 电影、以及尚未发现任何集数信息的订阅，保持"只抓排序第一名"。

检查结果会附带一条 `grab_note`（同时写入 event 的 `grab_note` 字段、检查提示
和「下载最优」提示），解释"抓取 0"的具体原因：未开启自动下载、下载器未初始化、
电影已有任务、没有达到评分线的候选、已播出集数均已下载、还有 N 集待补但没有
可覆盖且在预算内的候选、`DRY_RUN` 开启（附计划抓取数）或最后一条抓取错误。

> `更新至14集` 表示第 1–14 集的累积包，解析为 `episodes=1..14, is_batch=True`；
> 这样正在更新的剧不会因为包名里没有 `全N集` 而被当成"覆盖 0 集"，从而排在
> 单集 4K 种子之后、只下载到部分剧集。

### 7.6 去重

1. `torrent.mt_id` 唯一。
2. `episode_state`：覆盖集合中任一集已处于 `grabbed` 及以上 → 单集种子跳过；合集仅在缺失集数 ≥ 阈值时保留，且后续只整理缺失集。
3. 指纹：`normalize_title(发布名) + size_bytes` 在**同一订阅**内重复 → 跳过；
   剧集还要求覆盖集数相同，否则单集与合集不会被误判为重复。
4. 无法解析集数的整季合集抓取时不会写 `episode_state`，因此在其处于
   `grabbed/downloading/completed` 期间，同订阅不再接受另一条整季合集，避免重复下载。
5. 人工忽略（`state='ignored'` 且 reason=manual）永久生效，不再复活。

## 8. 服务设计

### 8.1 `SubscriptionService`

```python
def list(kind=None, status=None) -> list[Subscription]
def get(sub_id: int) -> Subscription
def create(data: SubscriptionCreate) -> Subscription
def update(sub_id: int, patch: SubscriptionPatch) -> Subscription
def delete(sub_id: int) -> int                        # 软删除；删候选池；返回清理条数
def due(now: datetime) -> list[Subscription]          # 到期、active、未删除
def mark_checked(sub_id, *, error: str | None = None, delay_min: int | None = None)
def progress(sub_id) -> Progress                       # 已整理 / 待补集数
```

- `delete(sub_id)`：写 `deleted_at` 软删除订阅，并在同一事务内删除该订阅的
  `candidate`/`ignored` 行（候选池没有下载价值）。`grabbed/downloading/
  completed/organized/failed` 任务行保留：任务页、仪表盘计数与每日日报通过
  `subscription.deleted_at IS NULL` 隐藏它们，qB 保种和已整理文件不受影响，
  已组织任务仍由保种策略按分享率/做种时长继续清理。
- 已下载集数由 `episode_state` 推导（整理 + 下载中），不额外维护计数器。
- 总集数来自 `total_episodes`：优先 PT 发布描述，缺失时用豆瓣
  `episodes_count` 补全；`available_episode` 表示已上线到第几集。
- 进度展示：总集数已知时显示 `总 X 集 · 已下载 Y 集 · 待下载 Z 集 ·
  待上线 N 集`；总集数未知但已上线集数已知时显示"已上线至第 X 集"；
  两者都未知时显示"总集数待定"。
- `episode_from/to` 为空且总集数未知时，进度只显示已下载集数与已上线集数。
- `update()` 可修改除 `kind` 外的订阅字段；`library_category` 会去首尾空白并截断到
  40 字符，空字符串存为 `NULL`（整理时按类型回退）。

### 8.2 `SearchService`

```python
def check_subscription(sub_id: int, *, manual: bool = False) -> CheckSummary

@dataclass
class CheckSummary:
    subscription_id: int
    searched: int
    candidates: int
    ignored: int
    grabbed: int
    error: str | None
```

流程：

1. 检查冷却、预算、订阅状态。剧集订阅先按豆瓣 subject 补齐 `original_title`、别名、
   年份，并按标题里的季号校正 `season`（该季已有 `episode_state` 时不改）；这次豆瓣
   查询与第 5 步的总集数查询共用。
2. 关键词：基础标题（去季后缀）→ 完整标题 → 基础英文原名 → 英文原名 → 别名，
   去重后最多搜索 3 个；电影仍追加“标题 + 年份”。只有找到“可用”的种子（标题/ID
   匹配，且未被体积、分辨率、做种数、日预算等硬条件直接排除）才提前停止；否则继续
   下一个关键词，避免只搜到超预算的 4K 合集而错过 1080p。
3. 调 `mteam.search(keyword, mode=..., categories=..., page_size=100, wait=not manual)`；`mode` 返回错误时自动回退 `normal`，每次检查只回退一次。手动检查的第 1 个关键词不等待限速槽位，后续关键词最多等待 20 秒；若仍被限流，保留已搜到的结果继续评估（不会整次失败）。
4. 逐条 `matcher.evaluate`：
   - 通过 → upsert `state='candidate'`；
   - 标题匹配但其他项不满足 → upsert `state='ignored', ignored_by='auto'`（每次最多 `max_candidates` 条）；
   - 标题都不匹配 → 只记 debug 日志，不落库。
5. 若冲突行是 `ignored_by='manual'` → 永不改写；`ignored_by='auto'` 且本次通过 → 复活为 `candidate`。
6. `auto_grab` 且非 dry-run 且分数最高者 → `download.grab()`。
7. 更新 `last_checked_at`、`error_count`。

手动搜索：`wait=False` 拿不到限速槽位时抛 `RateLimitBusy(retry_after)`，UI 提示稍后再试；不排队、不阻塞请求超过 1 秒。

### 8.3 `DownloadService.grab`

```python
def grab(torrent_id: int, *, actor: str) -> None
```

前置：`DRY_RUN=true` 时**不改变任何状态**，只写一条 event（`dry-run: would grab mt_id=...`）并返回。避免污染状态机。

状态与副作用：

```text
BEGIN IMMEDIATE
  UPDATE torrent SET state='grabbed' WHERE id=? AND state='candidate'
  if rowcount == 0: return（已被处理/已被人工忽略）
COMMIT

try:
  url  = mteam.gen_download_url(mt_id)          # 计入 torrent 预算
  data = mteam.download_torrent(url)            # 不带 x-api-key
  meta = bencode.parse_torrent(data)
  save_path = QB_SAVE_PATH
  # 先落库 hash/files，再调 qB：即使 qB 超时，下次也能按 hash 接管
  persist(qb_hash=meta.info_hash, files=select_files(meta), save_path=save_path)
  qb.ensure_category(QB_CATEGORY)
  qb.add(data, save_path=save_path, category=QB_CATEGORY, tags=[QB_TAGS],
         seeding_time_limit_min=min_seed_hours*60, ratio_limit=min_ratio)
  state='downloading'; grabbed_at=now
  upsert episode_state='grabbed'
except Exception as e:
  state='failed'; error=str(e)
```

- **抓取前二次校验**：覆盖集若已有 `grabbed` 及以上的 `episode_state`，单集种子直接拒绝（409）；合集中只对缺失集写状态。
- `episode_state` 写入使用 `INSERT ... ON CONFLICT DO UPDATE ... WHERE state != 'organized'`，**不允许把已整理的集降级**。
- 重试：取种/网络失败退避 3 次；若 qB 中已存在同 `info_hash`，视为成功接管，不重复添加。
- `episode_state` 只在 qB 添加成功后写入，失败**无需回滚**。
- 本地 `.torrent` 存一份到 `DATA_DIR/torrents/{mt_id}.torrent`，便于复盘与重解析。
- `Poller` 会处理停留在 `grabbed` 但 `qb_hash` 已存在的记录（进程中断后的自愈）。

### 8.4 `Poller`

```python
def poll() -> PollSummary
```

1. 取 `state IN ('grabbed','downloading')` 的记录。
2. `qb.info(hashes)`。
3. 映射：
   - 找不到且 `grabbed_at` > 10 分钟 → `failed`（qB 丢任务）。

### 8.5 `Organizer`

```python
def organize(torrent_id: int) -> OrganizeResult
def organize_pending() -> list[OrganizeResult]
```

前置条件：`state in ('completed','organize_failed')`，且距 `completed_at` ≥ `ORGANIZE_DELAY_SEC`，且 `DRY_RUN=false`。

流程：

1. 确定源文件基准目录（`files[].path` 相对于它解析）：
   - 优先实时读取 qB 的 `content_path`（本次整理时点最新，最可靠），其次用完成时落库的
     `torrent.content_path`；再回退到 `save_path`（或 `QB_SAVE_PATH`）经 `PATH_MAP_JSON`
     转本地路径。
   - `content_path` 是文件时，候选基准为「父目录」和「祖父目录」；是目录时，候选基准为
     「父目录」和「该目录本身」。候选必须落在 `DOWNLOAD_DIR` 内且存在。逐一尝试，取**第一个
     能让 `files[].path` 命中的基准**（都不命中时取第一个候选，便于错误信息定位）。
   - 原因：qB 的「创建子文件夹」布局会把单文件种子包进目录；而只有一条 `files` 记录的种子，
     qB 报出的 `content_path` 是**文件**路径 `<save>/<name>/<file>`，若直接取父目录会把
     `<name>/` 重复一次。
2. 定位单个文件时先试 `base/path`；找不到时在同级子目录中按文件名查找（仅当恰好一个候选时
   采用，多个候选报错，不猜）。仍找不到时，错误信息附带目录内前 10 个条目，便于定位。
3. **记录与实际不一致时以 qB 为准**：若记录中的视频文件在以上基准里一个都找不到，而 qB 的
   `content_path` 指向现存文件或目录，则改用 qB 实际内容（目录内全部文件）整理，并记录
   WARN 事件「记录的文件与 qB 实际内容不一致，按实际文件整理」。`content_path` 指向
   `DOWNLOAD_DIR` 根目录时不做扫描，避免误收其他种子。
4. 取 `files` 中视频文件（`select_videos`）：
   - 扩展名：`mkv/mp4/ts/m2ts/avi/mov/wmv/webm`；
   - 排除路径含 `sample|extras|featurette|behind|trailer|preview`（忽略大小写）；
   - 小于 `MIN_VIDEO_SIZE_MB` 排除；
   - 多文件时保留全部正片；单文件时取最大；
   - 多个文件解析到同一集 → 只保留最大者并告警。
5. 剧集：`resolve_episodes` 得到映射；任一视频无法映射 → 整体失败（不部分整理），原因写 `error`。
   已处于 `organized` 的集跳过（合集补集场景）。
   电影：跳过本步，直接使用电影模板。
6. 渲染目标路径（§9.1，`category` 来自订阅的 `library_category`，空值按 `kind`
   回退为电影/电视剧），校验目标在 `LIBRARY_DIR` 内；目标父目录不存在则创建。
   模板未写 `{category}` 且订阅显式设置了分类时，渲染结果中顶层的 `Movies`/`TV`
   目录替换为该分类（见 §9.1），使「媒体库分类」在默认模板下也能生效。
7. 逐文件硬链接：
   - 目标存在且同大小 → 跳过（幂等）；
   - 目标存在但不同 → 加 ` (2)` 后缀并告警；
   - `EXDEV` → 按设置 `copy`（默认）或 `symlink`，并记录事件。
8. 字幕：同名 `.srt/.ass/.ssa/.vtt` 链接到对应视频的目标同目录；源字幕在视频同目录
   查找（兼容单文件被 qB 子目录包裹的情况）。
9. 可选 NFO（订阅级开关）。
10. `organized_paths` 记录本次创建的库内目标路径；**重新整理**（`state=organized` 且
    `force=true`，如修改分类/模板后）时，先按新目标建链，再删除本任务旧记录或旧分类位置
    中已不再使用的链接（只限 `LIBRARY_DIR` 内、只删文件，下载副本不受影响）。
11. 事务更新 `state='organized'`、`organized_at`、`organized_paths`，分集状态 `organized`。
12. 收尾：电影 → 订阅置 `done`；剧集达到 `episode_to` 且目标集全部 `organized` → 订阅置 `done`。
13. 失败时回滚本次已创建的链接（unlink），状态 `organize_failed`，保留错误信息供重试。

### 8.6 `SeedingService`

```python
def cleanup(dry_run: bool = False) -> list[Deletion]
def disk_usage() -> DiskUsage
```

删除条件（全部满足）：

1. `state='organized'`；
2. 做种时长 ≥ `min_seed_hours`；
3. 单种分享率 ≥ `min_ratio` **或** 做种时长 ≥ `max_seed_hours`；

- 再按"做种最久 + 已达标"顺序强制清理，直到降到阈值以下。

分集状态的清理规则：

- 自动清理（只删 `organized`）→ `episode_state` 保留。
- 人工删除未整理的种子 → 删除其覆盖集中**状态不是 `organized`** 的行，允许以后重新抓取。
- 人工删除已整理的种子 → 保留 `organized` 行，不重复下载。

### 8.7 `ProfileGuard`

```python
def refresh() -> MTeamProfile
def check() -> GuardAction
```

- 每 15 分钟取一次 `/member/profile`，写 `account_snapshot`。
- `ratio < ratio_pause_all` → 设全局抓取暂停 + 高优通知（只通知一次，恢复时再通知）。
- `ratio < ratio_pause_nonfree` → 只允许免费种子。
- 字段解析容错：找不到 ratio 时跳过判定，不能因解析失败误停。

> 站点建议分享率不低于 0.6（社区经验为低于 0.3 封号），护栏值全部可配。

## 9. 路径与命名

### 9.1 模板与占位符

允许的占位符（白名单，未知即启动失败）：

`library` `category` `title` `original_title` `year` `season` `episode` `episode_end` `resolution` `video_codec` `ext` `group`

默认模板：

```
movie_path_template = "{library}/Movies/{title} ({year})/{title} ({year}) - {resolution}.{ext}"
tv_path_template    = "{library}/TV/{title} ({year})/Season {season:02d}/{title} - S{season:02d}E{episode:02d}.{ext}"
```

`category` 取订阅的“媒体库分类”，可在新建订阅时自由填写（预设 电影 / 电视剧 /
动漫 / 纪录片 / 综艺）；留空时电影回退为 `电影`，剧集回退为 `电视剧`。

默认模板不含 `{category}`，以保持既有媒体库路径；但只要订阅**显式设置了分类**，
渲染结果中顶层的 `Movies`/`TV` 目录会被替换为该分类：

```
电影 + 分类=动漫：{library}/动漫/机器人之梦 (2023)/机器人之梦 (2023) - 1080p.mkv
剧集 + 分类=纪录片：{library}/纪录片/剧名 (2025)/Season 01/剧名 - S01E01.mkv
```

留空分类时仍为 `Movies` / `TV`。模板中已写 `{category}` 时按模板原样渲染，不做替换，
需要完全自定义位置时使用 `{library}/{category}/{title}/...`。

多集文件：`S01E01-E03`。

### 9.2 命名规则

- `title`：订阅中文名优先；没有则用 `original_title`；再没有才用清洗后的发布名。
- 年份未知时省略 `({year})`（模板渲染阶段做条件替换）。
- 文件名清洗：去掉 `<>:"/\|?*`、控制字符、首尾空格与点；单段长度 ≤ 180 字节。
- 路径必须落在 `LIBRARY_DIR` 下（`realpath` 校验），否则拒绝。

### 9.3 极影视适配

- 极影视的实际扫描目录与命名偏好**以 M1 实测为准**，模板可改，不需要改代码。
- M1 验收标准：整理后的文件在极影视中能被识别为正确剧集/集数；若失败，先调模板，再考虑 NFO 兜底。

## 12. 安全设计

1. **API Key**：默认由 `config.py` 从环境变量读取；设置页可保存本地 SQLite 覆盖值（`.env` 作为回退）。日志与异常统一做掩码（`mte_***`）；不写入 URL；不返回给前端（页面只显示已配置/未配置）。
2. **下载 URL**：`download_torrent` 不带 `x-api-key`；URL 视为一次性凭证，不落日志。
3. **密码**：管理端密码来自 `ADMIN_PASSWORD`，使用 `hmac.compare_digest` 做常量时间比较；`.env` 以明文保存，需限制文件权限且不要提交。
4. **Session**：Starlette `SessionMiddleware`，`HttpOnly`、`SameSite=Lax`、`max_age=7d`；`SESSION_SECRET` 持久化。
5. **CSRF**：Session 内随机 token，所有 POST 表单/接口校验 `X-CSRF-Token` 或隐藏字段。
6. **登录节流**：进程内按 IP 计数，5 次失败锁 5 分钟。
7. **路径越界**：所有目标路径 `realpath` 后必须位于 `LIBRARY_DIR`；所有读取路径必须位于 `DOWNLOAD_DIR`。
8. **种子安全**：限制大小/文件数；不执行任何内容；不跟随 tracker 重定向到非预期主机（下载 URL 仅允许 http/https 且长度受限）。
9. **最小暴露**：默认只监听 `0.0.0.0:8080`（可用 `PORT` 修改），由宿主机防火墙限制；README 明确建议仅内网。

## 17. 与概要设计的差异说明

- 搜索最小间隔从 60s 调整为 **20s**（可配）。理由：60s 会让 UI 手动搜索长期阻塞；站点预算 400/24h 已足够保守。
- 类型判断从"依赖分类 ID"改为"**集数语义优先，分类 ID 可选**"。理由：分类 ID 尚未实测，不能作为硬依赖。
- 新增 `account_snapshot`、`job_run` 两张表；`files` 只存视频/字幕，避免大包把库撑大。
- 明确 qB 与本地两套路径命名空间及 `PATH_MAP_JSON`。
- 明确 `episode_offset` 语义：`display = parsed + offset`（例：第二季第 1 集发布名写 E13 → offset = -12）。

以上差异已同步回概要设计。
